# Source fixture data model

This is a provenance-preserving export contract for a frontend migration. It is not a newly designed production HR database. The mobile project already contains its demo fixtures, business formulas, form templates and local preview stores; the web frontend retains those workflows. There is no MySQL connection or new backend.

The export and web migration both read the delivered `source-snapshot` baseline. This immutable copy prevents simultaneous edits in the original mobile workspace from changing one half of the delivery. The export includes the four `no/` legacy dashboard pages for completeness; the active navigation inventory contains 118 pages.

## Storage contract

| Table | Meaning |
| --- | --- |
| `export_metadata` | Export version, fixed snapshot date, counts, source manifest, hashes and limitations. |
| `source_assets` | Exact source bytes, path, MIME type, byte length and SHA-256. Includes HTML, JS, CSS, JSON, SVG and supplied raster images. |
| `source_pages` | Initial browser title and visible text snapshot for every source HTML page. References the exact source asset. |
| `form_fields` | Each initial DOM input, select or textarea, including hidden controls. JSON stores identifiers, labels, placeholders, values, attributes, validation flags and select options. |
| `datasets` | An initializer or standalone literal with its source location and exact expression. Stores the evaluated JSON value, or SQL NULL with `source_only` and an explanation. |
| `dataset_records` | Every array entry in an evaluated dataset. A JSON Pointer identifies its exact location; nested arrays and repeated occurrences remain separate. |
| `employee_references` | Employee number/name pairs found in objects and recognized source tuples. Each source occurrence is preserved independently. |

Relations are `source_assets → source_pages → form_fields` and `datasets → dataset_records / employee_references`. Records are not silently moved between unrelated business modules.

## Extraction phases

`static_evaluation` evaluates only individual initializer expressions in a fresh VM context with no Node, filesystem, network or DOM APIs. It can reproduce data transforms such as `Object.freeze`, array mapping and source date generation. Evaluated values are snapshots generated by the source expression; their expression remains available.

`static_literal` captures constant arrays or objects inside deferred functions, including `initial()` fixtures that are not created until a workflow opens. This fallback retains constants without requiring user input or running approval actions.

`runtime_initialization` runs each original page in local Chrome and captures actual array/object initializers as the page loads. Remote CDN requests are blocked. The browser clock is fixed to the export snapshot date in `Asia/Kuala_Lumpur`, and local preview storage starts empty. Shared scripts are recorded separately for every page that initializes them, so these entries include intentional duplicates and UI state.

`source_only` means an expression depends on a form, DOM node, callback parameter, later interaction or another unavailable runtime value. It retains its exact expression and error message. It does not represent a missing transaction or a generated substitute. A runtime snapshot of the same expression can also exist as a separate provenance record.

Offsets and line numbers are relative to the script body. `script_index` distinguishes multiple inline script elements within an HTML file. `initialized_by_page` shows which page initialized an external script in a runtime snapshot.

## Value fidelity

Employee numbers are VARCHAR values throughout; `0000101`, `004177` and `EBB01` retain their leading zeros and original spelling. Rendering places `#` before the number; the data remains unprefixed when the original source is unprefixed.

The exporter does not resolve conflicting names or profiles attached to the same employee number in different demos. Source counts, summary totals and incomplete lists retain their original values; it does not invent additional rows to make a summary match a visible list.

Static JavaScript values without a native JSON representation use explicit descriptors such as `$type: function`, `undefined`, `bigint`, `date`, `regexp`, `map` or `set`. Function descriptors preserve their source. Runtime repeated references can use `$type: repeated_reference`; exact original code is always available in the source archive. Dates already represented as source strings remain strings.

HTML-only text, hardcoded payslip lines, policy text, declarations, dynamically inserted form templates and attachment filenames remain in the exact archived source, even when they do not form an independently evaluated dataset. Supplied images are preserved as binary data without inferred transcription. No production database, private uploaded attachments or API data was provided.

The SQL uses hexadecimal UTF-8 conversion for textual values and binary literals for source bytes. This prevents apostrophes, backslashes, CRLF, Unicode text and HTML from being changed by SQL escaping. Empty strings and JSON null are distinct from SQL NULL. Source arrays preserve order; JSON Pointers identify each row without manufacturing relational keys.

## Frontend usage and future backend

`public/data/seed.json` is a portable read-only export of pages, fields, datasets and employee references. It is about 11 MB and should be loaded lazily if needed for administration or inspection. Actual interactive preview state is managed by the frontend's existing local stores. Changing the preview does not overwrite this immutable export.

Before a future production backend is added, define validated domain tables for employee, attendance, approval, payroll, claims, project work and workplace processes. This export supplies the original facts, field inventory and fixtures for that work; it does not claim that source snapshots or repeated UI state are already a normalized production model.

## Verification evidence

`node database/verify-export.mjs` checks all 276 archived assets against the frozen source bytes and SHA-256, covering 9,179,114 bytes. It decodes and compares all 41,540 JSON rows in datasets, form fields, array records and employee references, verifies JSON paths, preserves employee leading zeros, and checks known hours-costing, new-user profile, payroll-pending and generated attrition fixtures. An explicit path can be supplied to validate a different mobile-source version.

The export inspected 122 source pages and 158 external/inline script bodies, with zero parsing or page initialization errors. It contains 1,166 controls, 339 selects, 1,671 select options, 6,671 dataset snapshots and 30,867 array entries. Of the snapshots, 257 are explicitly `source_only`. There are 2,836 employee occurrences representing 194 distinct source employee numbers, not a claimed production headcount.

MySQL 8 was selected by the user. A MySQL server is not installed in the current workspace; the generated SQL and all payloads were validated, but an actual server import has not been run.
