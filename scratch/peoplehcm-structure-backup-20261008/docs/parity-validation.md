# Source-preservation validation

Run `node --test --test-isolation=none tests/parity.test.mjs` after `npm run migrate`. The test uses Node's built-in runner and needs no dependencies. It compares against the immutable `source-snapshot` shipped with this project, so changes in a separately open mobile repository do not change the baseline. To compare against another original-project location, set the `SOURCE_ROOT` environment variable. An explicitly configured but unreadable source path fails validation.

The suite checks all 118 original routes, every source-manifest asset, unchanged external business JavaScript/CSS/data/images, exact original inline business-script hashes, and recorded post-migration HTML hashes. It also checks adapter dependencies, all local HTML CSS/JavaScript references, and the eleven formerly missing source destinations repaired through aliases. Query strings and fragments do not change a local asset's filesystem destination. Existing markup before a malformed doctype is retained and does not itself fail the test.

When the source snapshot is available, the suite additionally compares the entire migration asset set and original asset hashes, every input/select/textarea, every option, every inline script, and HTML outside the explicitly allowed presentation changes. Those permitted changes are local font/icon resources, the responsive viewport, an initial light-theme/presentation marker to prevent a mobile-theme flash, and dependencies marked `data-web-presentation`. Field IDs, values, constraints, options, inline handlers and business-script bodies must remain exactly unchanged.

When the frontend is moved to another computer without its source snapshot, it validates against `docs/source-manifest.json`. Source HTML entries must contain `webSha256` for migrated bytes, `inlineScriptsSha256` for original inline bodies, and `fieldMarkupSha256` for original controls. Other assets retain their original `sha256`. The source-snapshot comparisons are explicitly skipped; the manifest, complete copied asset set, script/control hashes, dependencies and alias checks still run. The manifest is a reproducible local integrity record, not an independent audit signature.

These tests establish source preservation and route/dependency coverage. They do not prove every runtime branch, layout, translation or user interaction works. Browser verification must exercise forms, validation, persistence, date filters, pending approvals, comments, charts, attachment controls and return navigation. Existing alert-only submissions and export demos retain their frontend behaviour; they are not server transactions.

## Inventory review

`docs/feature-parity.md` separates source-preserved functions from existing backend/demo limitations and states that static extraction does not prove runtime behaviour. Its control totals count occurrences, including repeated templates and shared scripts, rather than distinct business fields. All 118 route titles have Chinese translations; coverage of runtime screen text requires the adapter's translation dictionaries and browser checks. Original data such as employee names, codes, numeric values and request references must not be translated or changed.

The source contains eleven navigation links whose destinations were absent. Alias files should redirect to existing complete `leave.html`, `me.html`, `change-request.html` or `index.html` screens and activate the relevant existing section. Alias existence alone cannot prove that the correct leave tab or profile section activates; browser navigation checks must verify it.

Some source JavaScript files counted by the inventory are root-level development helper scripts that are not imported by application HTML. The migration manifest covers application assets and all actual external script dependencies rather than these unused helper files. Presentation and shell code are additional frontend assets and intentionally have no original-mobile hash.
